# متطلبات الأمان الإلزامية — حقيبة الأستاذ

> هذه القائمة إلزامية بالكامل. لا تُعتبر مرحلة "لاحقة"، بل معيار قبول (Acceptance Criteria) في كل مرحلة من `04-tasks-phases.md`.

## 1. عزل لوحة المدير
- تُبنى وتُنشر كمشروع Cloudflare Pages منفصل تمامًا (`apps/admin`) على نطاق فرعي مستقل (مثل `admin.<domain>`)، معزول عن تطبيق الأستاذ.
- **Cloudflare Access (Zero Trust)** أمام النطاق الفرعي بالكامل: لا وصول لصفحة تسجيل الدخول قبل التحقق من البريد عبر Access.
- **حماية مضاعفة إلزامية**: Access يتحقق فقط من هوية البريد؛ لا يكفي وحده. كل طلب داخل `apps/admin` يجب أن يتحقق أيضًا من دور المستخدم الإداري في الخادم (`core/auth` + جدول `user_roles`). أستاذ يتجاوز Access بأي طريقة (مثال: بريد أُضيف بالخطأ) يجب أن يُرفض ثانية من فحص الدور.
- **دخول المدير لكلتا اللوحتين**: لا حساب مزدوج؛ حساب المدير نفسه (بدوره الإداري) مسموح له بفتح `app.<domain>` (تطبيق الأستاذ) أيضًا دون قيود الاشتراك، عبر كوكي جلسة مشتركة على الدومين الجذر (راجع `03-plan.md` §6).

## 2. المصادقة والجلسات
- مصادقة ثنائية (2FA/TOTP) إلزامية لكل حساب مدير بدون استثناء.
- JWT قصير الأمد (صلاحية 15 دقيقة) + Refresh Token قابل للإلغاء + قائمة "الجلسات النشطة" مع تسجيل خروج عن بُعد من كل الأجهزة.
- Turnstile إلزامي على كل نموذج تسجيل دخول (المدير والأستاذ).
- تنبيه بريدي فوري عند تسجيل دخول من جهاز/موقع جغرافي جديد.
- (اختياري للحماية القصوى) قائمة IP مسموح بها لحسابات Super Admin فقط.

## 3. الصلاحيات
- RBAC دقيق (Super Admin / Content Admin / Support / Billing) بدل `isAdmin` واحد.
- كل مسار API يتحقق من الصلاحية في الخادم دائمًا (RBAC للمدير، Plugin entitlement للأستاذ)، بصرف النظر عن إخفاء العنصر في الواجهة.
- سجل تدقيق (Audit Log) غير قابل للتعديل لكل عملية حساسة (من فعل ماذا ومتى).

## 4. حماية المدخلات والبيانات
- تحقق صارم من كل مدخل (schema validation، مثل zod) في كل مسار API قبل أي كتابة.
- Prepared Statements فقط في D1 — ممنوع تجميع نصوص SQL يدويًا (منع SQL Injection).
- تعقيم (sanitize) أي محتوى مولَّد بالذكاء الاصطناعي قبل عرضه في الواجهة — ممنوع حقن HTML خام (منع XSS).
- حماية CSRF على كل طلب يغيّر حالة (state-changing) — أو استخدام SameSite cookies + رموز CSRF.
- ترويسات أمان (CSP، X-Frame-Options، HSTS) مفعّلة عبر Cloudflare.

## 5. الحد من الاستغلال (Rate Limiting)
- حدود صريحة على: تسجيل الدخول (منع Brute Force)، إدخال كود التفعيل (منع التخمين)، استدعاءات توليد AI (منع استنزاف التكلفة)، لكل IP ولكل مستخدم.
- ضبط الحدود قابل للتعديل من لوحة المدير حسب الباقة.

## 6. أكواد التفعيل
- كود فريد بصيغة تتضمن checksum يمنع التخمين، استخدام واحد فقط (`used` بعد أول استعمال)، تاريخ انتهاء صلاحية مفروض في الخادم لا في الواجهة فقط.

## 7. الأسرار والبيانات الحساسة
- كل مفتاح/سر (AI API key، مفتاح البريد، JWT secret) يُخزَّن فقط كمتغيرات بيئة مشفّرة في Cloudflare، أبدًا في الكود المصدري أو Git.
- تدوير دوري للأسرار، وصلاحيات محدودة (Least Privilege) لكل توكن Cloudflare API يُستخدم في CI/CD.
- توكن Cloudflare API المستعمل من GitHub لنشر التحديثات وتطبيق ترحيلات D1 (راجع `03-plan.md` §7) يُخزَّن في "GitHub Actions Secrets" (أو إعدادات النشر التلقائي لـ Cloudflare Pages) بصلاحيات محدودة فقط (Pages + D1 على المشروع المحدد)، لا صلاحية حساب كاملة (Global API Key).

## 8. النسخ الاحتياطي والاستمرارية
- تصدير/نسخ احتياطي دوري لقاعدة D1 (CSV أو تفريغ SQL) يُخزَّن في R2.
- سياسة الاحتفاظ بالملفات في R2 محددة بوضوح.

## 9. المراقبة والتنبيه
- تسجيل ورصد الأنشطة المشبوهة (محاولات دخول فاشلة متكررة، حجم استدعاءات غير طبيعي) مع تنبيه فوري للمدير.

## 10. قبل الإطلاق (Pre-Launch Checklist)
- [ ] مراجعة كل بند أعلاه فعليًا منفَّذ (لا نظريًا فقط).
- [ ] فحص تبعيات الحزم (`npm audit` أو أداة مماثلة) بلا ثغرات حرجة.
- [ ] اختبار محاولة دخول لوحة المدير من خارج Access (يجب أن تُرفض تمامًا).
- [ ] اختبار استخدام كود تفعيل مرتين (يجب أن يُرفض ثانيًا).
- [ ] اختبار استدعاء مسار API لموديول غير مفعَّل للمستخدم مباشرة (يجب أن يُرفض بصرف النظر عن الواجهة).
