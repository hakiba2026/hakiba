# مراحل تنفيذ المشروع — حقيبة الأستاذ (Spec Kit Phases)

> قاعدة: لا تبدأ مرحلة جديدة قبل تسجيل اكتمال المرحلة الحالية في `PROGRESS.md` (راجع `10-progress-log-template.md`) **و** تحديث `MAP.md` (راجع `12-feature-map-template.md`). كل مرحلة تنتج تسليمات قابلة للتحقق (Acceptance Criteria).

## المرحلة 0 — التحضير والإعداد
**الهدف:** بيئة عمل جاهزة قبل كتابة أي كود ميزة.
- التحقق من اكتمال كل بنود `11-pre-setup-checklist.md` (حسابات Cloudflare، Wrangler، دومين، مفاتيح...).
- تهيئة مستودع Next.js فارغ (بنية `/apps/web` و `/apps/admin` و `/core` و `/modules` و `/reference`، راجع `03-plan.md`) + `wrangler.toml` لكل تطبيق + ربط كل تطبيق بمشروع Cloudflare Pages مستقل.
- تهيئة D1 وKV وR2 (بالأسماء المتفَق عليها) وربط bindings في `wrangler.toml` لكل تطبيق.
- استخراج قالب الواجهة المرفق (Shadcn Dashboard) إلى `/reference/shadcn-dashboard-template` وقراءة `08-dashboard-template-integration.md` قبل أي بناء واجهة.
- ربط مستودع GitHub بكل مشروعي Cloudflare Pages (نشر تلقائي عند كل push)، وتفعيل خطوة تطبيق ترحيلات D1 تلقائيًا بعد كل نشر ناجح (راجع `03-plan.md` §7).
**تسليم:** مشروعان فارغان (أستاذ + مدير) يُبنيان ويُنشران بنجاح تلقائيًا على مشروعي Cloudflare Pages المرتبطين بـ GitHub (صفحة "قيد الإنشاء" لكل واحد)، وقالب الواجهة موجود في `/reference` جاهزًا للاستخراج.

## المرحلة 0.5 — دراسة المشروع القديم وتحويله (اختيارية، عند توفر Laravel Filament)
**الهدف:** إن وُضع مشروع Laravel Filament + MySQL القديم في `/reference/legacy-laravel-filament`، يجب دراسته بالكامل قبل أو بالتوازي مع المرحلة 2، حسب `13-legacy-laravel-migration-guide.md`.
- دراسة الـ migrations وseeders والنماذج (Models) والعلاقات، ومقارنتها ببنية `07-db-schema.sql` الحالية، وتحديث المخطط عند الحاجة (بعد موافقتي).
- دراسة Filament Resources/Actions/Policies لفهم منطق العمل الفعلي (لا فقط الشاشات)، لتحويله لصفحات ومسارات API في `apps/admin` و`apps/web`.
- إنتاج قسم أولي في `MAP.md` (راجع `12-feature-map-template.md`) يسرد كل ميزة موجودة في المشروع القديم، وحالتها في المشروع الجديد (مُحوَّلة / قيد التحويل / لم تُحوَّل بعد).
**تسليم:** تقرير مطابقة (Laravel ⇄ Next.js) داخل `MAP.md`، ومخطط `07-db-schema.sql` محدَّث ومتوافق مع البيانات القديمة.

## المرحلة 1 — الأساس البرمجي المشترك (Core)
**الهدف:** بناء `/core` بالكامل قبل أي module.
- `core/db`: عميل D1 + أول ترحيل (migration) لجداول القسم 2 من `07-db-schema.sql`.
- `core/i18n`: تبديل AR/FR + RTL/LTR تلقائي على مستوى `<html dir>`.
- `core/auth`: تسجيل دخول/خروج، جلسات JWT قصيرة الأمد + Refresh Token (راجع `06-security.md`).
- `core/plugin-registry`: قراءة `manifest.ts` من `/modules` وحساب صلاحيات المستخدم.
- `core/ui-kit`: استخراج وتكييف `AppHeader`/`AppSidebar`/مكوّنات shadcn/ui من القالب المرفق في `/reference/shadcn-dashboard-template` (وليس بناءً من الصفر)، حسب `05-design-system.md` و`08-dashboard-template-integration.md`، مع تفعيل دعم RTL/LTR عبر `direction.tsx`.
**تسليم:** تسجيل دخول يعمل، تبديل لغة يعمل (مع انعكاس فوري للاتجاه RTL/LTR)، تخطيط Header/Sidebar مطابق للقالب المرفق وثابت وresponsive في كلا تطبيقي `apps/web` و `apps/admin`، بدون أي module فعلي بعد.

## المرحلة 2 — قاعدة البيانات الكاملة
**الهدف:** تطبيق كل مخطط `07-db-schema.sql` (مستخدمون، أدوار، باقات، اشتراكات، أكواد تفعيل، plugins، تصنيف أكاديمي، jobs، audit_log).
**تسليم:** كل الجداول موجودة في D1 مع بيانات seed أولية (باقة تجريبية واحدة، مادة/مرحلة تجريبية واحدة).

## المرحلة 3 — لوحة تحكم المدير العام (تطبيق منفصل)
**الهدف:** تطبيق `apps/admin` منفصل تمامًا، محمي بحماية مضاعفة (Cloudflare Access + فحص دور في الخادم — راجع `03-plan.md` §6 و`06-security.md`).
- شاشات: المستخدمون، الباقات، الاشتراكات، التصنيف الأكاديمي، إعدادات الموقع، RBAC (الأدوار)، سجل التدقيق — مبنية فوق مكوّنات القالب المرفق (Sidebar/Header/Tables/Forms) حسب `08-dashboard-template-integration.md`.
- Sidebar المدير يستعمل نمط `nav-items` من القالب، بقائمة ثابتة لشاشات الإدارة (لا تعتمد على plugins كما في تطبيق الأستاذ).
**تسليم:** مدير Super Admin يمكنه تسجيل الدخول (عبر Access + 2FA) وتنفيذ كل عمليات CRUD المذكورة في `02-spec.md` §4، **و**: (أ) حساب أستاذ عادي يُرفض تمامًا عند محاولة فتح `admin.<domain>` (من Access أولاً)، (ب) نفس حساب المدير يستطيع فتح `app.<domain>` (تطبيق الأستاذ) بنجاح دون أي حظر.

## المرحلة 4 — الاشتراكات وأكواد التفعيل والبريد الصادر
**الهدف:** تدفق كامل من تأكيد الدفع إلى تفعيل الاشتراك.
- توليد كود تفعيل فريد + checksum، ربطه بمزوّد بريد خارجي (Resend/Brevo/Postmark)، شاشة إدخال الكود عند الأستاذ.
**تسليم:** اختبار كامل يدوي: إنشاء كود من لوحة المدير → استلام بريد فعلي → تفعيل الاشتراك بنجاح من حساب أستاذ تجريبي.

## المرحلة 5 — لوحة تحكم الأستاذ + نظام الصلاحيات/Plugins
**الهدف:** الهيكل العام لتطبيق الأستاذ، فوق نفس مكوّنات القالب المستعملة في لوحة المدير (تجربة بصرية موحّدة).
- Sidebar يعرض فقط الـ plugins المفعّلة فعليًا (حسب `02-spec.md` §5) باستعمال نمط `nav-items` الديناميكي من القالب، شاشتا "صلاحيات الباقات" و"صلاحيات فردية" في لوحة المدير.
**تسليم:** تغيير باقة مستخدم تجريبي ينعكس فورًا على الأدوات الظاهرة له، والتحقق يعمل أيضًا عبر استدعاء API مباشر (اختبار Postman/cURL).

## المرحلة 6 — موديول توليد الدرس (lesson-generator)
**الهدف:** أول module فعلي كامل، يُستخدم كنموذج مرجعي لكل الموديولات اللاحقة.
- معالج "إضافة درس جديد" (11 خطوة، `02-spec.md` §6)، تكامل مزوّد الذكاء الاصطناعي، نظام الطابور (`03-plan.md` §3)، تصدير PDF/Word.
**تسليم:** أستاذ تجريبي يولّد درسًا فعليًا من البداية للنهاية عبر الواجهة على الموبايل.

## المرحلة 7 — موديولات التمارين والامتحانات
**الهدف:** تكرار نمط المرحلة 6 لـ `exercise-generator` و `exam-generator` (مع سلّم تنقيط وحلول).
**تسليم:** توليد فرض وامتحان كاملين بنجاح.

## المرحلة 8 — مكتبة الأستاذ والتصدير
**الهدف:** حفظ كل المحتوى المولَّد، بحث/تصفية، إعادة تصدير.
**تسليم:** مكتبة تعرض كل عناصر أستاذ تجريبي مع تصدير يعمل.

## المرحلة 9 — الأمان والتحصين (Security Hardening)
**الهدف:** تطبيق كل بند في `06-security.md` كمراجعة شاملة قبل الإطلاق (لا كإضافة لاحقة فقط).
**تسليم:** قائمة تحقق أمنية موقّعة (كل بند في `06-security.md` منفَّذ ومُختبَر).

## المرحلة 10 — الاختبار وضمان الجودة (QA)
**الهدف:** اختبار كل تدفق رئيسي (تسجيل، اشتراك، توليد، تصدير) على شاشات موبايل حقيقية، واختبار AR وFR.
**تسليم:** تقرير اختبار بلا أخطاء حاجبة (blocking bugs).

## المرحلة 11 — الإطلاق (Launch)
**الهدف:** نشر الإصدار الأول للجمهور.
- ربط الدومين النهائي (والنطاقين الفرعيين `app.` و`admin.`)، تفعيل النسخ الاحتياطي الدوري، مراجعة أخيرة لـ `06-security.md`، تأكيد أن كل push على GitHub ينشر تلقائيًا على كلا مشروعي Cloudflare Pages مع تطبيق ترحيلات D1 تلقائيًا (راجع `03-plan.md` §7).
- تحديث `MAP.md` النهائي (راجع `12-feature-map-template.md`) ليعكس كل ما هو مكتمل فعليًا في الإصدار الأول، وما تأجَّل لإصدار لاحق.
**تسليم:** المنصة تعمل على الدومين النهائي وقابلة للتسجيل والدفع الفعلي، و`MAP.md` يعكس الحالة الحقيقية للمشروع بدقة.

## المرحلة 12 — المراقبة والتحسين بعد الإطلاق
**الهدف:** استمرارية.
- مراقبة الأخطاء والاستخدام وتكلفة AI، جمع ملاحظات الأساتذة، تخطيط الميزات التالية (بنك أسئلة، تحليلات الطلاب...).
**تسليم:** تقرير أسبوعي أول لمقاييس الاستخدام والتكلفة.
