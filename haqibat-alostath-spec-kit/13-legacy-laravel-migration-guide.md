# دليل دراسة وتحويل المشروع القديم (Laravel Filament + MySQL ← Next.js)

> يُستعمل هذا الملف فقط عند وضع مشروعك القديم في `/reference/legacy-laravel-filament`. الهدف: تحويل كامل، لا إعادة كتابة عشوائية — دراسة دقيقة أولًا، ثم تحويل مطابق للمنطق مع تكييفه لبنية `04-tasks-phases.md` و`01-constitution.md` (عزل modules، Cloudflare-only، إلخ).

## 1. ترتيب الدراسة الموصى به

1. `database/migrations/*` — لفهم بنية الجداول الحقيقية (الأعمدة، الأنواع، المفاتيح الأجنبية، الفهارس) — قارنها ببنية `07-db-schema.sql` الحالية.
2. `database/seeders/*` — لفهم البيانات الأساسية المطلوبة (مثل التصنيف الأكاديمي، باقات افتراضية).
3. النماذج (Models) وعلاقاتها (Eloquent relationships) — لفهم منطق الترابط بين الجداول عمليًا، لا فقط بنيويًا.
4. Filament Resources/Pages/Actions/Widgets — هذه تمثل شاشات لوحة المدير الفعلية؛ كل Resource ≈ شاشة إدارة كاملة (قوائم + نماذج + إجراءات) يجب أن تصبح شاشة مكافئة في `apps/admin`.
5. Filament Policies / أي middleware صلاحيات — لفهم منطق الصلاحيات الحالي، ومطابقته أو تحسينه حسب `06-security.md` (RBAC).
6. أي Jobs/Queues/Notifications في Laravel — لتحويلها لمنطق `core/queue` (جدول `jobs` + Cron) بدل بنية Laravel Queue.
7. أي مسارات API (لو موجودة) موجّهة لتطبيق موبايل/واجهة خارجية — لتحويلها لمسارات Next.js API Routes بنفس المنطق.

## 2. قواعد التحويل الإلزامية

- **لا نقل حرفي أعمى**: مطابقة منطق العمل (business logic) مطلوبة، لكن البنية التقنية تتبع دائمًا `01-constitution.md` (عزل modules، لا Laravel-style MVC كامل داخل module واحد ضخم).
- **قاعدة البيانات**: MySQL (auto-increment integers عادة) ← Cloudflare D1 (SQLite). قرارات يجب اتخاذها **بعد سؤال مالك المشروع**، لا افتراضها:
  - هل تُستبدَل المفاتيح `AUTO_INCREMENT` بمعرّفات نصية (UUID/TEXT) لتتوافق مع `07-db-schema.sql` الحالي، أم يُحتفَظ بمفاتيح عددية للجداول المنقولة من Laravel؟
  - كيف تُعالَج فروقات الأنواع بين MySQL و SQLite (مثل `ENUM`, `JSON`, `DECIMAL`)؟
- **الصلاحيات**: أي نظام صلاحيات Laravel (Spatie Permission أو ما شابه) يُعاد بناؤه بمنطق RBAC الموجود في `06-security.md`، لا يُنسخ كحزمة Laravel.
- **الملفات المرفوعة**: أي تخزين ملفات محلي/S3 في المشروع القديم ← Cloudflare R2.
- **البريد/الإشعارات**: أي Laravel Notifications/Mail ← مزوّد البريد الخارجي المعتمد في `01-constitution.md` (Resend/Brevo/Postmark).
- **لا يُنقَل أي سرّ فعلي** (مفاتيح API قديمة، كلمات سر قاعدة بيانات) من المشروع القديم إلى المشروع الجديد أو إلى Git — فقط البنية والمنطق والبيانات التجريبية/الأساسية (seeders).

## 3. التسليم المطلوب من antigravity بعد الدراسة

- قسم 7 من `MAP.md` (راجع `12-feature-map-template.md`) معبَّأ بالكامل: كل ميزة في المشروع القديم مقابل حالتها في المشروع الجديد.
- تحديث `07-db-schema.sql` (بعد موافقة مالك المشروع) ليعكس أي حقول/جداول ضرورية اكتُشفت من المشروع القديم ولم تكن موجودة في المخطط الأولي.
- قائمة أسئلة توضيحية لمالك المشروع (إن وُجدت) حول أي قرار تحويل غير محسوم، قبل تنفيذه.

## 4. تنبيه

هذا التحويل عمل ضخم؛ يجب تنفيذه كمهام صغيرة متتابعة (module تلو الآخر من المشروع القديم)، مع تحديث `PROGRESS.md` و`MAP.md` بعد كل جزء، لا كمهمة واحدة كبيرة غير قابلة للمراجعة.
